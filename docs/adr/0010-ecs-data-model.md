# ADR 0010: ECS data model

- Status: Accepted
- Date: 2026-09-02

## Decision
The phase 1 ECS is defined by seven decisions, taken together because each of them is a breaking migration if it is added later.

**1. Entity identity.** An `Entity` is an opaque 64-bit handle: a 32-bit index and a 32-bit generation, the generation non-zero so that `Option<Entity>` costs eight bytes rather than sixteen. Despawning bumps the generation, and that is what makes a stale handle detectable. The index returns to a free list threaded through the entity slots themselves, and is handed out again last-in-first-out. A slot whose generation would wrap is retired rather than reused: losing one index in four billion is cheaper than issuing a handle indistinguishable from an ancient one.

**2. Storage kind is a property of the component type.** A component declares whether it lives in a table column or a sparse set. Table storage is the default and is what queries iterate densely. Sparse storage is for markers and for components that are added and removed constantly, where an archetype move per toggle costs more than the slower iteration.

**3. Archetypes over table components only.** An archetype is the set of table-stored component types an entity has; entities with the same set share columns. Adding or removing a table component moves the row to another archetype, through cached edges so the common path is a lookup and a memcpy per column. Adding or removing a sparse component moves nothing.

**4. Structural change is deferred and explicit.** Systems record spawns, despawns, insertions and removals into `Commands`; the world applies them at a stage boundary. Nothing observes a half-applied structural change, and a system's view of the world does not shift under it while it runs.

**5. Change detection is by tick, not by dirty flag.** Every component row carries the tick it was added and the tick it was last mutably borrowed; a system compares against the tick it last ran. A system that runs every third frame therefore sees changes from all three, which a boolean flag cleared at end of frame cannot express.

**6. Hooks and required components are part of insertion, not conventions on top of it.** A component type may declare an `on_add` and an `on_remove` hook, run by the world at the point the structural change is applied, and may declare components that must exist alongside it, inserted with their default when they are missing. Bundles are not a concept in this ECS: a bundle is a value that has to be kept in step with the type it describes, while a requirement is a property of the type itself.

**7. Relationships are first-class; the hierarchy is one of them.** An edge is a pair of a relation type and a target entity, stored on the source entity, with a reverse index maintained by the world so the targets of a relation can be found without a scan. Despawning an entity removes the edges that name it. Parent/child is the `ChildOf` relation and gets no bespoke storage. Walking a relation goes through the component accessor described below rather than through query iteration, because a parent and its child usually sit in the same column.

The ECS crate keeps `#![forbid(unsafe_code)]` through phase 1. A query borrows a component type as a whole - not a column per archetype - and iterates the borrowed storage by index: the borrow is checked once per component per query rather than once per entity, and the inner loop is a pair of slices with no per-element check. The granularity is the deliberate part. A per-archetype borrow would let the same aliasing mistake pass or panic depending on which archetype the other entity happened to land in, which is a defect that reproduces only on some data; borrowing the component type makes the failure the same every time.

Reaching a second entity's component while holding that borrow therefore goes through an accessor the world provides, not through a second borrow. A borrowed component offers `get` and `get_mut` by entity, and a disjoint form that takes several entities at once and fails when two of them coincide rather than aliasing. The hierarchy is its first user, and it needs the accessor whatever the granularity is: the reverse index of a relation is held by the world rather than stored as a component, so a node and its parent carry the same component set, sit in one archetype and share one column - an archetype-level borrow would not separate them either. The public API never hands out `&mut [T]` over a whole column. Slicing a borrow by hand along archetype boundaries is physically sound and unchecked, and the way to keep it from becoming the habit is to leave nothing to slice.

The attribute binds this crate, not its dependency graph, so the synchronization a parallel scheduler will need can come from a vetted crate without lifting it. Phase 1 schedules systems in one thread, so that question is not open yet. The decision is revisited when the scheduler needs disjoint mutable access across threads, or when the phase 1 benchmark measures the safe formulation against an unsafe spike and the gap is large enough to be worth a contained exception. Borrow granularity is a separate question with its own trigger: it moves from the component type to the pair of archetype and component when a traversal cannot be expressed through the accessor inside its frame budget, or when a parallel executor rules two systems compatible on disjoint archetypes and the runtime check has to be at least as fine as that ruling. Note which direction that is: widening turns panics into successes and changes no signature, while narrowing would break working code, which is why the strict form is the one to start from. Either revisit is a new ADR naming the module it applies to, not a general licence.

## Reasons
- Storage kind per component type is Bevy's answer to the same problem and it is the right one: a single storage strategy is wrong for either markers or bulk data, and which one a component is cannot be decided by the engine. Unity's DOTS chunk layout shows the ceiling of the dense case, and it is high enough that the default should be table storage.
- Deferred structural change is what makes deterministic system order meaningful. If a system could split an archetype while another iterates it, the order in which systems observe the world would depend on when memory moved, and the recorded-input replay that phase 1 exits on would not reproduce.
- Tick-based change detection is a precondition for fixed timestep. With a fixed step the render and simulation rates differ by construction, so any "changed since last frame" flag is already answering the wrong question.
- Hooks exist so that render and physics can register an object as it appears, instead of a synchronization system that scans for what appeared since last frame. That scan is the thing that makes engines feel like they have a frame of lag in the editor.
- Required components replace bundles because bundles are duplication: the same set of components is described in two places, and the copy that is wrong is discovered at runtime. Bevy carried bundles first and replaced them later, which is exactly the migration this ADR exists to avoid.
- Relationships as a first-class concept, with the hierarchy built on top, is Flecs' design. The alternative - a `Parent`/`Children` pair maintained by hand - is the same reverse index written once per relation, which is why every engine that starts there ends up with a second, incompatible mechanism for the next relation it needs.
- Reuse order is deterministic whichever end of the free list it comes from, and the generation catches a stale handle either way, so the choice is settled by which order makes mistakes louder. Immediate reuse does. The defect that actually outlives an entity is a side table indexed by entity index and never cleared on despawn, and reuse order decides whether it corrupts data on the next spawn or after a hundred thousand of them - the first is caught by a test, the second by a user. Immediate reuse also returns a slot that is still in cache.
- Access metadata per archetype and component is what a parallel executor needs to decide which systems may run together, and it is computed from the archetypes a query matches. That is a layer above storage: the executor can gain it later without the borrow model or any signature changing. What `forbid(unsafe_code)` does cost is the option Bevy takes, where the storage checks nothing and the executor's proof stands in for it; here the check has to become as fine as the executor's decisions instead, which is work inside the accessor.
- Safe Rust is affordable at this granularity. What makes people reach for `unsafe` in an ECS is proving aliasing and checking bounds per element; borrowing once per component per query and then walking slices moves that cost to the query, where it is paid a handful of times a frame instead of a hundred thousand. What is left is a borrow that fails loudly instead of a compiler error, which is a worse diagnostic and not a worse guarantee.

## Consequences
- The public surface of `engine-ecs` in phase 1 is `Entity`, `World`, `Query`, the component accessor, `Commands`, the component trait and its derive, the relation type, and the hook signatures. Everything else is internal, because ADR 0005 starts constraining this surface at 0.1.0.
- Determinism becomes testable and must be tested: component ids are assigned in a deterministic registration order, archetypes are visited in a deterministic order, and no iteration order derives from a `HashMap`. The phase 1 exit criterion - a recorded input that replays to an identical world state - is what proves it.
- A component type is a registered type (ADR 0003): storage kind, requirements and hooks are metadata on the same registration the inspector and serialization will read, not a second registry.
- Entity identity is 64 bits and appears in serialized authoring data only through the `AuthoringId` mapping of ADR 0004. A saved scene never stores an `Entity`.
- The accessor arrives with the query layer, not with the hierarchy that first needs it: it is the random-access half of the same surface, and ADR 0005 starts constraining that surface at 0.1.0. Its natural implementation is `slice::get_disjoint_mut`, which is stable since 1.86 and absent from the 1.85 recorded as MSRV, so it carries a deliberate MSRV bump under the policy in CONTRIBUTING. Until that bump the same traversal is expressible by cloning the parent value out and writing the child afterwards, which holds no two borrows at once and costs one copy per node.
- The phase 1 benchmark runs at 1000 entities, which is the ROADMAP exit criterion, and at 100 000, which is where the safe and unsafe formulations can be told apart at all. At a thousand entities both disappear into the noise, so a criterion at that size measures that the code runs, not that it is fast enough.
- Reverse indices for relationships cost memory per relation type and make despawn O(edges naming the entity) rather than O(1). That is the price of not scanning, and it is paid at despawn rather than every frame.
