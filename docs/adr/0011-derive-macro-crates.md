# ADR 0011: Where derive macros live

- Status: Accepted
- Date: 2026-09-02

## Decision
A derive macro is generated by a proc-macro crate owned by the crate whose trait it implements, named `<owner>-macros`. Phase 1 creates two: `engine-core-macros` for the reflection derive of ADR 0003, and `engine-ecs-macros` for `Component` and the relation derive of ADR 0010. There is no single workspace-wide macro crate.

Six rules make that ownership real rather than nominal.

**1. The owner re-exports the derive under its own name.** A user writes `engine_ecs::Component` and never names a macro crate; `engine-ecs-macros` is an implementation detail of `engine-ecs` the way a backend is an implementation detail of the crate that owns it (ADR 0009).

**2. Generated code names the owner crate and nothing else.** Anything an expansion needs from a third crate is re-exported by the owner through a `#[doc(hidden)]` module kept for that purpose, and the macro emits the path through it. `#[derive(Component)]` attaches component metadata to the ADR 0003 registration, which lives in `core`, so it emits `::engine_ecs::__private::...` rather than `::engine_core::...`.

**3. A macro crate depends on proc-macro tooling only.** It never names a workspace crate: the owner already depends on it, and the reverse edge would be a cycle.

**4. The owner depends on its macro crate with an exact version requirement.** Generated code names items the owner re-exports, so a version skew between the two is a compile error at best. All workspace crates already share one version and ship together.

**5. An owner declares `extern crate self as <owner>;`** so that rule 2 holds for the owner deriving on its own types, where `::engine_ecs::` would otherwise not resolve.

**6. Ownership is a table in `cargo xtask check-deps`.** A macro crate named by any crate other than its owner fails the build, and an owner that no longer names its macro crate fails it too. This is the mechanism already used for backend ownership, extended by one table.

Adding a `<owner>-macros` crate later follows this decision and does not need a new ADR. One shared helper crate - a normal library, not a proc-macro crate - is likewise pre-authorized, once the same attribute parsing has been written a third time. Nothing else about the layout is pre-authorized: a second macro crate under one owner, or a macro crate shared by two owners, is a new decision.

Diagnostics are part of the surface: an attribute the derive rejects produces a `syn::Error` spanned on the offending token rather than an error inside expanded code, and every rejection path in an attribute grammar carries a compile-fail test.

## Reasons
- **The ownership rule is the one this repository can already check.** `cargo xtask check-deps` enforces that a backend crate is named only by its owner, and the same table shape carries over unchanged. A single workspace macro crate has no such rule available: it would be named by `core`, `ecs`, `asset` and eventually more, so "owned by" degenerates into "listed in the workspace", which no tool can verify and no reviewer can violate.
- **Incremental rebuild is the product metric this project measures itself by, and a shared macro crate sits upstream of everything.** It would be a dependency of `core`, so editing the ECS derive would rebuild `core` and every crate behind it - the whole workspace - to change code that only `ecs` expands. Per-owner crates put the blast radius where the change is. The ROADMAP budget of ten seconds for an incremental gameplay rebuild is the number this protects.
- **Rule 2 is what keeps the boundary checker honest about generated code.** A macro crate depends on no workspace crate, so `check-deps` sees no edge for what it expands into: a derive emitting `::engine_core::` from a crate that reaches `core` by no recorded path would be an undeclared dependency that the graph cannot show. Forcing expansion through the owner makes every path in generated code follow an edge that exists.
- **The coupling between the two derives is a call, not shared codegen.** ADR 0010 requires component metadata to be attached to the ADR 0003 registration rather than to a second registry, which sounds like an argument for one crate. It is not: the `Component` derive emits a call to a public registration API of `core`, the same call a hand-written implementation would make. What the two derives genuinely share is attribute parsing and generics handling, which is why a shared helper crate is pre-authorized on evidence of duplication rather than in advance.
- **Bevy arrived here from the other direction.** It has `bevy_ecs_macros`, `bevy_reflect_derive`, `bevy_asset_macros` and a small `bevy_macro_utils`, which is the layout this ADR starts from. Starting at the end state skips a rename that touches every crate.
- **Proc-macro crates are host-only.** They are compiled for the machine running the build even when the target is Android, so `syn` never reaches a shipped game binary and costs build time rather than binary size.
- **The choice is reversible and was still worth deciding now.** Because rule 1 keeps the macro crate out of every user-visible path, merging or splitting macro crates later is an internal refactor. What is not reversible is writing the first derive against no rule at all and discovering the layout afterwards, one crate at a time.

## Consequences
- Two crates enter the workspace in phase 1: `crates/core-macros` and `crates/ecs-macros`, each a published member sharing the workspace version.
- `syn`, `quote` and `proc-macro2` enter the dependency graph. All three are `MIT OR Apache-2.0`, already permitted by the allow-list in `deny.toml`, and their MSRV is far below 1.85. `syn` becomes the heaviest compile-time dependency in the workspace; that cost is the price of the derive-based registry ADR 0003 chose over a hand-maintained one, and it is paid on the host.
- `xtask` gains a macro-ownership table and the rule over it, added in the pull request that creates the first macro crate. `ARCHITECTURE.md` gains the crates and the boundary.
- The `#[doc(hidden)]` re-export module is public API in the technical sense. It carries no compatibility promise, and the ADR 0005 snapshot records it as an explicitly unstable item so that a change to it is visible in review rather than silent.
- A derive cannot be exercised from the crate that defines it: a proc-macro crate exports macros and nothing else. Helper functions inside it can be unit-tested, but the expansion is tested from the owner, where the trait is - which is also where the test belongs.
- Every crate that later wants a derive gains a crate rather than a module. That is the cost of the decision, and it is the reason a second one is not added speculatively: `asset` gets `engine-asset-macros` when it has a derive, not before.
